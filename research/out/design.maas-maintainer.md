## Verdict
APPROVE WITH CHANGES — the version-primary, code-grounded framing and the per-tenant (legacy vs praxis) 3.6 model are right, but the fact base contains verifiable errors about what shipped in 3.4/3.5/3.6, the "3.5 GA" scene is built on an unresolved ConfigMap-shape conflict, and the migration flow misrepresents the trigger and omits designed-for failure states.

## Critical

1. **The "3.5 GA" scene rests on the wrong ConfigMap shape, and the plan contradicts itself about it.** The repo's own migration compatibility table enumerates a distinct **ODH 3.5.0** field shape — no `model-provider-resolver` in pre-processing, **no `maas-headers-guard`** in processing, response `api-translation` ON (`docs/content/migration/upgrade-to-3.6.md:59`; baseline key `"odh-3.5.0"` in `plugins_migration.go:586`). The v0.2.1 git tag instead contains commit `e245289c` (2026-07-19, "add model-provider-resolver to ipp-pre, add maas-headers-guard to ipp") — the tag matches the `"default+response-api-translation"` baseline, not what the team's own docs call ODH 3.5.0. facts.md claims the matrix was "validated directly against repo tags, not release notes" but never reconciles this conflict. The design then splits the difference incoherently: B2 puts `model-provider-resolver` in pre-auth "[3.5 only]" and `maas-headers-guard` post-auth "[3.5]" (v0.2.1 shape), while B3's 3.5 flow outline says "ipp-pre (model-extractor)" (ODH-3.5.0 shape) yet keeps headers-guard post-auth — a chimera matching **neither** recognized baseline. Before Phase C, decide whether the 3.5 scene depicts the shipped ODH 3.5.0 product or the v0.2.1 tag and make B2/B3/facts.md agree; otherwise the visualizer misrepresents what 3.5 customers actually run — precisely what I'd be blamed for.

2. **The migration flow's first step ("operator sets annotation") misrepresents the trigger.** Per `platform_context.go:119-127`, an absent annotation means praxis, and nothing anywhere seeds `payload-processing-type: "ipp"` (repo-wide grep: only `platform_context.go` references the value). A 3.5 tenant upgraded to 3.6 has no type annotation and no status annotation (`seedPayloadProcessingStatusOnCreate` fires only at creation, `aitenant_controller.go:905-920`), so `reconcilePayloadProcessingSwitch` runs gate → cleanup **automatically on upgrade**, with no operator action. The only annotations an operator sets are `"ipp"` (opt back) and `force-payload-processing-migration=true` (unblock). The design's own B2 states "absent=praxis default," so B3's migration flow contradicts the design's own facts. Showing migration as opt-in when it is default-on hides the single most important fact about the 3.6 upgrade.

3. **The version matrix is factually wrong about gateway-default-deny, and the error propagates into the flows.** facts.md marks "gateway-default-deny TRLP, router-fallback auth anchor" as ✓ 3.6-dev only, but `deployment/base/maas-controller/policies/gateway-default-deny.yaml` has existed since `bdae2c84` (2026-03-05) and is wired into the policies kustomization at both v0.1.1 and v0.2.1 (verified via `git grep` at both tags). B3 then lists "plus gateway-default-deny TRLP" as a 3.6 addition on the legacy-tenant flow. Only the router-fallback auth anchor half of that row is genuinely 3.6-dev (`gatewayHasKuadrantWasmAuth` is absent from v0.2.1). Split the row; fix the flows.

## Important

4. **Significant 3.6 shipped-behavior changes are missing from the matrix, version overlay, and flows**: the rate-limit identity split — `selected_subscription_key` vs short `selected_subscription_id`, recommended downtime, brief fail-open window, sticky `status.rateLimitIdentity`, mixed-rate-group TRLP splitting (`upgrade-to-3.6.md:1-50`, release notes:35-38); the **RHCL 1.4→1.5 coupling** — on RHCL 1.4.x a provider error without token usage can hang callers with ≥2 subscriptions under an active TRLP (release notes:42) — exactly the kind of version coupling a maintainer expects surfaced; `X-MaaS-Tenant` header elimination (v0.2.1 breaking change, belongs in the 3.4→3.5 delta); llm-d-router apix v1alpha2 coupling for InferenceObjectives. B1's version-overlay paragraph covers none of these.

5. **The migration flow as outlined is not animatable and happy-path-only treatment is dishonest.** `reconcilePayloadProcessingSwitch` (`pipeline.go:297-445`) includes states the design omits entirely: the blocked marker (`payload-processing-migration=blocked`, Ready=False, force-annotation hint) with **two distinct block causes** (fingerprint gate, compat check — plus a third fails-closed block on assessment error); the apiTranslation **intent-persistence step** (`spec.apiTranslation.enabled: true` durably written *before* cleanup — a real step, not just a check); accepted-risk markers (`explicit-false`/`forced`) that persist in the Degraded condition *after* cleanup; the legacy flip-back pending state ("waiting for the praxis payload-processing cleanup…", `pipeline.go:438-445`); the legacy CAS-claim of `cleanup-complete`; and gate allow-paths for absent / already-praxis ConfigMaps (`plugins_migration.go:117-140`). B2's AGC-node overlay list covers only the annotation default, cleanup-complete/steady, operand cleanup, and the race guard. The compat check blocks every Azure/Vertex/Bedrock binding — for many real tenants the blocked branch is the *expected* path, and the operator remedy (force annotation, or `apiTranslation=false` with its targetModel/path-rewriting side effects) is the content users actually need.

6. **The "3.6 TP" badge asserts a support level nobody has decided.** The release-notes mapping table lists 3.6 as "Planned" (TBD); nothing in the repo designates praxis-in-3.6 as Tech Preview. Since 3.6 is unreleased and main is a moving target (HEAD `8d30ae9a`, 2026-11-10 — e.g. "Anthropic messages no longer block migration" is recent main-only behavior), the honest label is provenance-based: "3.6 (dev · main @ commit · unreleased)" on the badge and per feature, with a defined re-verification step at cut. Hard-coding "TP" is a product claim made by a visualizer.

7. **Per-tenant selection: faithful on the main rule, two caveats missing.** (a) SkipIPP is resolved only for AITenant-managed MaasTenantConfigs; legacy `Tenant` objects always deploy IPP (`platform_context.go:67-116`) — the binary legacy/praxis split silently ignores that population. (b) B3 says the 3.6 legacy flow is "identical to 3.5" while B2 says response plugins "3.6(ipp) = empty again" — both can't be true, and neither is reliably true: an upgraded legacy tenant keeps its preserved (`managed=false`) 3.5 ConfigMap (possibly with response api-translation), while a fresh `"ipp"` tenant gets the HEAD default (`response: []`). The response-plugins depiction needs a "depends on the tenant's preserved ConfigMap" caveat — which is exactly what the fingerprint gate checks.

8. **Terminology: the total "IPP" ban diverges from the product's own shipped docs.** "IPP"/"Inference Payload Processing" appears throughout user-facing documentation (upgrade-to-3.6.md ~15×; `user-guide/inference.md:23`, `install/external-model-setup.md:11`, release notes:88, `praxis-extproc/docs/migration-ipp-to-praxis.md`). The rationale (AGC reuses the `ipp` EnvoyFilter names for the praxis dataplane, so "IPP" is ambiguous) is sound for node labels, and the proposed replacements match deployment names (`payload-pre-processing`/`payload-processing`) and the image name (`praxis-extproc`) — good. But a user who reads the visualizer and then the real upgrade guide hits "IPP → Praxis" with no bridge. Keep the replacements; add a one-line alias in the relevant overlays ("legacy payload processing = 'IPP' in the upgrade guide") instead of banning the string even from prose.

## Minor

9. "14 legacy payload-processing operands" (B2, B3, and praxis-inv.md) is off by one: `ippResourcesForTenant` (`pipeline.go:811-833`) lists **13** refs (2 HPA, 2 Deployments, 2 Services, EnvoyFilter, NetworkPolicy, 2 DestinationRules, ServiceAccount, ConfigMap, ClusterRoleBinding).
10. The 3.6 praxis post-auth chain omits `request_id`: the AGC base `extproc.yaml` chain `ipp` runs `request_id`, with `intelligent_route`/`credential_inject` added by the per-tenant overlay ConfigMap.
11. B5 lists `stream_usage_inject` as a praxis-ai runtime capability while also citing the "praxis-ai v0.6.0 pin" — but v0.6.0 predates that filter (praxis-cap discrepancy note; extproc migration doc issue #44). Scope the capability list to the pinned rev or mark it "praxis-ai HEAD, not in the pinned extproc image."
12. EPP reorder is correctly scoped to the legacy tenant (it lives in the IPP EnvoyFilter; AGC's praxis EnvoyFilter has no InferencePool reorder — verified), but InferenceObjectives are created by the MaaSSubscription controller regardless of backend and are absent from the praxis-tenant flow's internal-model story.
13. facts.md cites v0.2.1 usage-logs at `envoy-otel-access-log.yaml:350-359`, but that dsci-managed path exists only at HEAD; v0.2.1's file is `deployment/components/observability/usage-logs/envoy-otel-access-log.yaml` (FILTER_STATE content claim verified correct — fix the citation path).

## Suggestions

- Turn Critical #1 into content: a small "3.5 field shapes" table in the 3.5 overlay (ODH 3.5.0 default / v0.2.1 tag default / HEAD) — the migration gate's three recognized baselines are precisely the shapes customers carry into 3.6.
- Animate the handshake as a first-class state diagram (absent → blocked{fingerprint|compat} → intent persist → cleanup → cleanup-complete → steady, plus the legacy claim/pending path), not a linear step list; the annotation state machine is what operators will actually debug.
- Surface version couplings (RHCL 1.5, llm-d-router apix v1alpha2) in prerequisites/legend — "the visualizer didn't tell me I needed RHCL 1.5" is a blameable failure.
- State the tag-to-release mapping (3.4=v0.1.1, 3.5=v0.2.1, per release-notes index) explicitly in B1's overlay and record the ODH-3.5.0 caveat there, so the scene's provenance is self-documenting.
