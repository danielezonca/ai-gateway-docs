## Verdict
APPROVE WITH CHANGES — the deployed-vs-runtime split is the right instinct and mostly fair, but the fact base gets pin-vs-HEAD wrong in both directions, the B5 "available in runtime" bucket conflates three different codebases, the B4 ghost card overclaims MCP dispatch for the actual deployed image, and the "AGC-deployed chain" description omits `request_id` and the route-scoped ExternalModel split.

## Critical

1. **B5 capability bucket conflates three codebases; "available in praxis-ai runtime" is not a coherent bucket.** The deployed artifact is the `odh-praxis-extproc` image, which pins **upstream `praxis-proxy/ai` v0.6.0** (`praxis-extproc/Cargo.toml:56-59`) and builds the **FIPS feature set** `responses,aws-sigv4,store-postgres-cert-auth` (`Makefile:183`; Containerfile builds FIPS by default). The B5 list mixes: (a) **fork-only filters** — `api_key_auth` exists only in `redhat-et/praxis-ai` (fork commit `070642d1`, "for maas-api key validation"); it does not exist in upstream `praxis-proxy/ai` at all (no `filters/src/api_key_auth/` upstream, no history); (b) **post-v0.6.0 upstream filters** — the `vertex` rawPredict (Anthropic⇄Vertex) filter was added 2026-10-16 (#1695), after v0.6.0 was cut 2026-10-09, so it is not in the deployed image; (c) **source-present but not compiled in** — `token_rate_limit` is behind the experimental `token-rate-limit-filter` feature which is in neither praxis-extproc's defaults (`aws-sigv4, policy-engine, responses-full`) nor the FIPS set; even `policy-engine` is absent from the deployed image. Presenting all of these as "available in praxis-ai runtime" next to a "praxis-ai v0.6.0 pin" note is internally inconsistent and would not survive a maintainer read.

2. **Inherited fact-sheet error on `stream_usage_inject` at the pin.** praxis-cap.md claims the pinned v0.6.0 "apparently predates it; NOT IMPLEMENTED IN CODE at the pinned rev." False: it was added upstream 2026-09-28 (#1231), v0.6.0 was tagged 2026-10-09, and it is registered **ungated** at v0.6.0 (`git show v0.6.0:filters/src/register.rs:215`). The praxis-extproc migration doc's "no Praxis filter injects `stream_options` today / no coverage anywhere" (`docs/migration-ipp-to-praxis.md:228-234`) is stale, not authoritative about the pin. The design doesn't repeat the error, but facts.md/praxis-cap.md must be corrected before B5 overlay text is written from them, and the charter's premise (pin lacks it) is itself wrong.

3. **B4 ghost card: "MCP dispatch" is too strong for the deployed runtime.** The deployed `odh-praxis-extproc` image is the FIPS build, which **excludes `responses-full`** — MCP tools (`openai-mcp-tools`), context compaction (`openai-compact`), Conversations, and the file resolver are *not compiled into the image* (`docs/fips.md:99-102`; `FIPS_FEATURES` at `Makefile:183`). The ghost card's list "openai_responses_request/store/rehydrate, agentic loop, MCP dispatch, WS passthrough, OpenResponses conformance" is accurate for praxis-ai source (and non-FIPS builds) but not for the runtime AGC actually deploys. Conversely the card is **too weak** on the sharpest fact: the Responses core (request kernel, store/rehydrate via cert-auth Postgres, agentic loop, Responses→CC translation — all in `openai-responses`/`store-postgres-cert-auth`) **is compiled into the deployed image, unused**; the gap is purely AGC config/CRD wiring. Say that — it's the honest headline a maintainer would insist on.

## Important

4. **The "AGC-deployed chain" is misdescribed: four ext_proc filters, two post-auth deployments, route-scoped enablement.** AGC deploys `ipp-pre` (pre: `model_to_header`, `llmisvc_model_provider_resolver`), `ipp` (base post-auth chain = **`request_id` only**, `config/manifests/praxis-extproc/base/config/configmap.yaml`), `external-model-pre`, and `external-model` (per-tenant chain `post-auth`: `intelligent_route` + `credential_inject`, generated in `pkg/tenant/extproc.go:176-199`). On controller-owned ExternalModel routes, `ipp-pre`/`ipp` are **disabled** and the external-model filters enabled with STREAMED request-body mode (`pkg/controller/reconciler.go:1119-1136`; `config/manifests/external-model/overlays/odh/external-model-envoy-filter.yaml:9-11`). The design's "post-auth: intelligent_route, credential_inject" describes only the ExternalModel path; also `credential_inject` is emitted only when credentials exist (`extproc.go:186-197`). B2/B3 must either scope the praxis flow to external models explicitly or show both paths — and `request_id` shouldn't silently vanish from the "as deployed" chain.

5. **No 3.6 internal-model (llm-d/KServe) flow.** 3.4 and 3.5 each have an Internal (llm-d) flow; the 3.6 set drops it, yet the pre chain's `llmisvc_model_provider_resolver` exists precisely for KServe publisher-ID routing, and the internal path's post-auth is `request_id`-only (no `intelligent_route`). Omitting it makes the 3.6 praxis story external-only and invites the misreading that `intelligent_route` handles all tenant traffic.

6. **Metering regression under praxis is unmentioned.** MaaS still deploys the usage-logs EnvoyFilter for praxis tenants (praxis-inv §1), but the AGC chain deploys no `stream_usage_inject`/`token_count`/`token_usage_headers`, so streaming requests to OpenAI-compatible backends carry no usage data (migration doc: "streaming token counting … has no usage data"). B3's "metering via Kuadrant TRLP unchanged" conflates rate limiting with usage-logs metering and hides a functional regression the design's own fact base documents. The overlay on the praxis dataplane should state it — and note the fix (`stream_usage_inject`) is already in the pinned image, just not in the AGC chain.

7. **Terminology: "praxis-ai v0.6.0" doesn't exist.** The redhat-et fork's tags stop at v0.3.0 (`git describe` → `v0.3.0-260-g8a9a2159`); the v0.6.0 pin is praxis-extproc → **upstream `praxis-proxy/ai`**. B5's "links to praxis-extproc + praxis-ai repos" is ambiguous between fork and upstream. Write "pins upstream praxis-proxy/ai v0.6.0 (via praxis-extproc)" and link upstream; link the fork only where fork-only capabilities (`api_key_auth`) are discussed. Otherwise a maintainer wince is guaranteed. ("praxis-extproc" for the dataplane container and "praxis" for the annotation/tenant are fine and match how MaaS and the projects name themselves.)

## Minor

8. **"OpenResponses conformance" overclaims scope.** The suite is triaged into supported/unsupported/inapplicable buckets and gates only the **supported subset** of the `openai_responses_to_chat_completions` translation filter (`tests/conformance/openresponses/manifest.yaml:1-26`; currently `unsupported: []`, but that's a coverage metric, not whole-API conformance). Qualify accordingly.

9. **`identity_header_guard` is documented as the `maas-headers-guard` equivalent** (`filters/src/identity_guard/mod.rs:9-11`: "Maps to IPP's maas-headers-guard plugin but is generic"). praxis-inv §3's "no praxis equivalent in code" is true only of the AGC chain; the B5 overlay should say "not deployed by AGC; runtime equivalent is `identity_header_guard`" rather than leaving the guard as uncovered.

10. **"Vertex" in the provider-translation list needs disambiguation**: `openai_chat_completions_to_vertexai_gemini` IS at v0.6.0; the `vertex` rawPredict filter is not (see Critical 1).

11. Consider noting the fail-open/fail-closed asymmetry in the overlay detail table: `ipp-pre` runs `failure_mode_allow: true` while `ipp`/`external-model` are fail-closed (envoy-filter.yaml) — exactly the kind of nuance the overlay format exists for.

## Suggestions

- Draw the B5 line in **three buckets**, not two: (1) "Deployed by AGC (in the rendered chains)", (2) "Compiled into the deployed odh-praxis-extproc image (v0.6.0, FIPS feature set) but not configured — e.g. Responses core + store, SigV4", (3) "praxis-ai source only, not in the deployed image — api_key_auth (ET fork), token_rate_limit, vertex rawPredict, MCP tools/compact/conversations". That is the split a maintainer would defend.
- Fix praxis-cap.md and facts.md on the `stream_usage_inject` pin claim (Critical 2) before Phase C cites them.
- Label the 3.6 praxis flow "Praxis tenant — external models (ExternalModel routes)" and either add a thin internal-model flow or a note on the praxis container explaining the route-scoped split.
- In the migration flow, the handshake arrow "AGC claims (`steady`)" is fine, but note the new-tenant seeding (`cleanup-complete` at creation) so viewers don't think every praxis tenant ran the migration.
