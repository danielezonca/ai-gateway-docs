## Verdict
APPROVE WITH CHANGES — the design is unusually honest about plan-vs-code and mostly fact-grounded, but it contains one uncited behavioral claim, an unresolved "which 3.5 GA?" contradiction, a terminology rule that fails its own unambiguity test against actual deployed resource names, and a 3.6 praxis flow that quietly drops the metering path its own B2 adds.

## Critical

1. **Uncited claim presented as fact (B5).** "Anthropic rejects unmappable CC fields (400 vs 3.5 silent drop)" appears nowhere in the fact base — not in praxis-inv §4 (which only says anthropic+messages passes the compat check), not in ipp-ga (whose Anthropic translator section documents field mappings, not rejection semantics), not in praxis-cap. This violates the plan's own C5 rule ("every step, filter name, header mutation traceable to research citation") and its stated Principle. Either cite it (from praxis-ai `anthropic_messages_request` validation code) or cut it.

2. **"3.5 GA" is ambiguous and the design picks one answer silently.** The plan's B2/B3 3.5 chain (pre: model-extractor + model-provider-resolver; post: + maas-headers-guard; response api-translation) matches the `v0.2.1` git tag (verified: `git show v0.2.1:...plugins-configmap.yaml`). But the migration doc — cited by the plan's own fact base — records **three** recognized RHOAI 3.5 shapes, including "ODH 3.5.0 default (no `model-provider-resolver` in pre-processing, no `maas-headers-guard` in processing)" (`models-as-a-service/docs/content/migration/upgrade-to-3.6.md:59`, and baseline `"odh-3.5.0"` in `plugins_migration.go:642-670`). So an operator debugging an actual 3.5.0 cluster may see a chain that contradicts the visualizer's "3.5 GA" scene. The facts.md matrix (tag-validated) and maas-3.5.md (migration-doc-validated) disagree, and the design never resolves it. For the primary debugging audience this is a correctness issue, not a footnote: the 3.5 scene (or its overlay) must state which baseline it renders and that other 3.5 shapes exist.

3. **The B2 terminology rule fails its own unambiguity test.** The rule maps "Payload Processor (ext_proc)" → 3.4/3.5 and "praxis-extproc" → 3.6. But AGC's praxis dataplane deploys resources literally named `payload-processing`, `payload-pre-processing`, `payload-processing-plugins`, ServiceAccount `payload-processing`, EnvoyFilter `payload-processing` (verified: `ai-gateway-controller/config/manifests/praxis-extproc/overlays/odh/...`, base configmap named `payload-processing-plugins`). The **same k8s names persist across both eras with different owners**. A 3.6 scene that labels these "praxis-extproc" while the 3.5 scene labels identical names "Payload Processor (ext_proc)" — and confines raw names to "quoted identifiers inside overlay detail tables" — guarantees exactly the confusion the rule was written to prevent: anyone correlating the visualizer with a live 3.6 cluster finds `payload-processing` Deployments under a node labeled "praxis-extproc". The design needs an explicit label→resource-name mapping table per era, and overlays that state the actual object names for both.

## Important

4. **3.6 praxis flow omits the usage-logs path and mislabels metering (B3 vs B2).** B2 adds the usage-logs path "3.5+", and praxis-inv §1 confirms MaaS still deploys the usage-logs EnvoyFilter for praxis tenants. Yet the B3 praxis-tenant flow outline contains no usage-logs step and says "metering via Kuadrant TRLP unchanged" — conflating *rate limiting* (Limitador/TRLP) with *usage metering* (OTel access logs), and contradicting B2's own per-version identity mechanism (header_to_metadata in 3.6). Same class of error: B3's 3.6 legacy tenant says "identical to 3.5 flow" while B2 says 3.6 identity is header_to_metadata, not 3.5's FILTER_STATE, and B2 says the 3.6(ipp) response chain is empty — an *upgraded* legacy tenant keeps its `managed=false` ConfigMap (response api-translation on), a *fresh* one gets the empty default. B2 and B3 must be reconciled.

5. **"3.6 TP" is an invented release status.** Every fact source says "3.6-dev (HEAD)"; nothing establishes Technology Preview status. B6 even uses "3.6-dev" tags for EPP reorder/InferenceObjectives while B1 badges the whole scene "3.6 TP". If RHOAI 3.6 ships with different content, the badge is wrong on day one. Use "3.6 (dev)" or similar until a real product status exists.

6. **The migration flow is a control-plane state machine forced through a request-packet animation engine.** The engine's semantics are request-lifecycle: blue request packets, green response packets, per-step HTTP inspector payloads, and **loop mode auto-enabled after 500ms** (visualizer.md §1) — a one-shot migration replaying forever is actively misleading. The plan specifies neither inspector content for migration steps nor loop behavior, nor how the `blocked` terminal state renders. A static/clickable state-machine panel (absent → blocked / cleanup-complete → steady, with the CAS-claim and race-guard edges) would be more honest than a Dot-animated "flow"; at minimum: lightup-only steps, loop disabled for this flow, blocked shown as a terminal red state.

7. **Per-tenant coexistence is under-communicated (charter Q1).** Two 3.6 flows is the right call, but the design never states in the version overlay that **both dataplanes run simultaneously in one 3.6 cluster, per tenant** — nor the sharper caveat from praxis-inv §1: legacy `Tenant` CRs (non-AITenant-managed) get no SkipIPP and **always deploy IPP in 3.6**, regardless of annotation. Without that, a reader reasonably concludes "3.6 = praxis" and misreads an all-IPP 3.6 cluster. Also unmentioned: AGC is a separately deployed component (MaaS does not deploy it — e2e runs AGC's own script).

8. **B5's "available in praxis-ai runtime" list conflates HEAD with the deployed pin.** The overlay bullet says "praxis-ai v0.6.0 pin" and then lists capabilities validated at praxis-ai HEAD `8a9a2159` — including `stream_usage_inject`, which praxis-cap explicitly flags as **NOT IMPLEMENTED at the pinned v0.6.0 rev** (extproc migration doc issue #44). The "deployed vs available" split is the right idea but the "available" side must be labeled with which rev it describes.

9. **Response api-translation is shown without its streaming caveat.** ipp-ga §3: response plugins run only on full buffered JSON bodies; for SSE responses **no response plugin executes** — the stream passes through verbatim. In the 3.5 GA external-Anthropic flow, streaming responses are therefore *not* translated back to OpenAI format. That's a major behavioral gotcha for exactly the debugging audience, and neither B3's flow step nor B5's parity note mentions it.

10. **Phase C omits the inspector entirely.** Per visualizer.md's own recipe, every new flow needs an `inspStepXxx` function and dispatcher branch; the inspector is half the product. C1–C6 never mention inspector content for the 3.6 flows, migration flow, or version-dependent payloads. Shipping 3.6 flows against the stale 3.5 inspector (`POST /llm/ext-anthropic/v1/chat/completions` payloads) would be actively wrong — worse than not shipping.

11. **Deployed praxis chain is subtly wrong.** B2's post-auth chain lists `intelligent_route` + `credential_inject`, omitting the base chain's `request_id` (verified in AGC base configmap, chain `ipp`), and `credential_inject` runs only "when credentials exist". For a design whose differentiator is exact chain fidelity, show it exactly.

## Minor

12. `gateway-default-deny TRLP` listed as a 3.6 legacy-tenant flow *step* — it's a standing policy (defense-in-depth 0-token 429), not a request-path step.
13. 3.5 EPP "natural position" needs a caveat: per maas-3.5 §4.1, under RHCL router-anchored wasm or router fallback the EPP **silently never runs** and pool traffic falls back to round-robin — that's why the 3.6 reorder exists. Showing EPP as an unconditionally working 3.5 hop overstates.
14. B4 leaves `responses-api/index.html`'s known-broken UI as-is (the `agentic` flow is unreachable from the select; `flowOrder` dead code — visualizer.md §3). One-line fix; leaving it under a mere provenance banner is odd.
15. SigV4 is auth-signing, listed under "provider translations" in B5.
16. Mobile splash stats "recomputed per version" should be *computed from flowMaps in code*, not hand-maintained — the current inconsistency exists precisely because they're manual.
17. B7 says "cross-link only" to enmaas-flow.html but no B-section specifies where the cross-link lives.

## Suggestions

- Add a **naming table** to B2: visualizer label → actual Deployment/ConfigMap/EnvoyFilter/chain names, per era, with owners (maas-controller vs AGC). This resolves Critical 3 and would have caught Critical 2's shape ambiguity too.
- In the 3.5 scene overlay, link the upgrade-to-3.6 baseline table so readers can identify which 3.5 ConfigMap shape their cluster has — this is the single highest-value artifact for the migrating-operator audience.
- Consider rendering the migration as a **state-machine panel** (distinct visual grammar from packet flows) rather than flow #6; it also sidesteps the loop-mode and inspector problems.
- Reconsider the 3.4 scene's cost/benefit: the current 3.4 content is admittedly inaccurate, and three versions × ~4 flows ≈ 10 hand-curated step arrays + 10 inspector functions on hard-coded `drawBounds` rects. If 3.4 stays, at least derive shared step builders from a declarative per-version chain spec so 3.7 is a data change, not a code change.
- Since flows within 3.6 are tenant-selected rather than version-selected, consider labeling the 3.6 flow-select entries with the selecting condition (e.g. "Praxis tenant (default)" / "Legacy tenant (`ipp` annotation)") — the plan half-does this; make the per-tenant mechanism visible in the flow labels themselves, not just the version overlay.
