## Verdict
APPROVE WITH CHANGES — the fact base and honesty principles are sound, but the design under-specifies the engine changes it silently depends on (version-keyed inspector dispatch, per-version node geometry vs. visibility, loop mode), contains internal contradictions about the 3.5/3.6 plugin chains, and mis-describes two of the code recipes it cites (activePathColor, "registered in binary").

## Critical

1. **B1/C1 as scoped ships a broken inspector.** `inspStep` dispatch is keyed on `activeFlow` + 1-based step number only, with the ext-flow cases 1–24 inlined in the dispatcher (`ai-gateway-flow.html:1128–1136`, cases at `:1140–1269`). The design's B3 gives all three versions flows keyed `ext`/`inc`-style with *different* step counts and content. Two `flowMaps['3.4'].ext` and `flowMaps['3.5'].ext` both dispatch into the same inline switch. B1/C1 ("version toggle + per-version flowMaps + badges") never mentions making the dispatch version-aware — if C1 lands before C3, every version except one shows wrong payloads. Inspector content is *not* in the step arrays; adding a flow requires both a step array and an inspector function (visualizer.md §1), and the design only budgets for the former.

2. **"Node/line visibility driven by `version`" cannot express what B2 requires.** Visibility toggling handles nodes that exist or don't; it cannot handle (a) the EPP *position* change between 3.5 and 3.6 (B2: "3.6 = reordered before router") — `N` is one static coordinate table and every arrow step carries hand-tuned `fromXOff/toXOff/yOff/waypoints` bound to specific coordinates (e.g. `flowExt` steps 8/15/18/21: `fromXOff: -170`, `toXOff: 275`); (b) 3.4's single-stage Payload Processor vs 3.5's split — unless the 3.4 scene is literally the 3.5 post-auth container alone, which the design doesn't say; (c) the 3.6 scene needing **both** the ipp stack (legacy-tenant flow) *and* the praxis-extproc stack (praxis-tenant flow) — two flows *within one version*. Visibility-by-version cannot show one and hide the other; it must be flow-driven (or flow+version), which contradicts B1's stated mechanism. This ambiguity is the direct cause of the node-explosion question and is unresolved.

3. **No layout plan exists for the node budget.** Current scene: 33 nodes at LW=1250/LH=1050, with the region x≈490–740 (between Kuadrant and IPP) the only free gap for a pre-auth container. The 3.6 scene, if both stacks are visible: pre-container + 2 plugins, post-container + 5 plugins + response section, praxis container + 4 filters, usage-logs node(s), AGC, ghost card, InferenceObjective(s), EPP/sched, pool + 4, Kuadrant + 2, gw, maas, 5 providers, user ≈ 42–46 nodes — a ~35% increase in the same logical canvas. `resize()` computes `sc = min(W/LW, H/LH)*0.98` (`:344–351`); growing LH to ~1300 for a control-plane strip drops sc to ~0.75 on a 1512×982 laptop, rendering `fs:12–14` plugin labels at ~9–10px. The design contains zero coordinates/rects; per the inventory recipe, `drawBounds` IPP section rects are hard-coded pixels (`:497–527`) that must be manually extended per version. This is the largest schedule risk and it's unaddressed.

4. **Internal contradictions on the 3.5/3.6 plugin chains — three distinct shapes are conflated.**
   - B2: pre-auth = "model-extractor, model-provider-resolver**[3.5 only]**". The v0.2.1 tag puts mpr in **both** pre and post chains (`git show v0.2.1:...plugins-configmap.yaml`: pre = model-extractor + model-provider-resolver; post = maas-headers-guard → stream-usage-enforcer → model-provider-resolver → api-translation → apikey-injection), and 3.6-dev's default legacy profile *also* has pre-mpr (praxis-inv.md:45). "[3.5 only]" is wrong under either reading of the bracket.
   - B3's 3.5 flow outline says `ipp-pre` (model-extractor) **only** — contradicting B2 and the tag.
   - B3 says the 3.6 legacy flow is "identical to the 3.5 flow", while B2 says "3.6(ipp) response plugins = empty again" — 3.5 GA has response api-translation ON. And the migration code's recognized `"odh-3.5.0"` baseline is a *fourth* shape (no maas-headers-guard, pre = extractor only; praxis-inv.md:47). The design must pick, per scene, which of tag-default / recognized-baseline / HEAD-default it depicts, and B2/B3 must agree.

## Important

5. **The activePathColor recipe is mischaracterized and incomplete.** The enmaas implementation is a *static per-node classification*, not path-direction following: `const activePathColor = key === 'f_meter_post' || n.color === '#3fb950' ? '#3fb950' : '#58a6ff'` (enmaas-flow.html:444). Ported verbatim: response-path activations of `gw`, `maas`, `epp` (all `#79c0ff`/blue), and `rlimit` (orange) flash **blue** — B6's "request blue / response green frames on active nodes" is not what the code does. Worse, it **breaks error frames**: `execStep` mutates `N[s.target].color = errColor` for ✗ lightups (`:1508`) and `drawBox` strokes `n.color` today (`:397–399`); if stroke switches to `activePathColor`, red 401/429 flashes disappear. A correct port needs an activation-color map (record the step's `c` when adding to `activeNodes`) plus an errColor exception — small, but not the "self-contained" recipe as stated.

6. **TP "dashed borders" collide with existing semantics.** `drawBox` already dashes **every** `type:'plugin'` node (`:400`: `if (n.type === 'plugin') ctx.setLineDash(...)`). All plugins in all versions are dashed today; reusing dashes for "3.6-only" conflates two legend meanings. Use amber stroke/badge alone.

7. **The migration flow is a poor fit for the Dot engine, and the design under-nodes it.** The facts describe an annotation state machine (absent → `cleanup-complete` → `steady`, CAS claims, one-shot deletion of 14 operands, blocked gates) — no packets, and B3's steps (operator annotation, ConfigMap fingerprint gate, compat check, cleanup) have no nodes: the design adds only the AGC node. Technically the engine can animate it (arrows + lightups + `errColor` for blocked gates), but a pentagon "request packet" flying from Operator→Gate→Cleanup misrepresents reconcile semantics. Alternatives: (a) lightup-only sequence on AGC/maas-controller nodes using existing badge (`✓`/`✗`) mechanics, no dots; (b) a dedicated HTML state-machine panel shown when the migration flow is selected, with the canvas depicting before→after (ipp stack via the existing `fading` set, praxis stack glowing); (c) reuse `responses-api/index.html`'s hidden `loop_area` node + waypoint-loop pattern for the reconcile-retry loop. At minimum the design must add operator and maas-controller nodes to B2's node list or cut the animated flow.

8. **`praxis-flow.html` is entirely ignored.** The repo already contains a fourth sibling visualizer — 1509 lines, "Praxis — Rust AI Proxy (pingora)" with `api_key_auth`, `identity_header_guard`, `external_metering`, etc. (commit 73abbc9). It appears in neither the plan's repos-in-scope, nor Phase A's visualizer inventory, nor B7's cross-link decisions. After this redesign the repo will carry **three** praxis depictions (praxis-flow, enmaas-flow, the new 3.6 scene) with three different chains — a contradiction and maintenance risk the "no enmaas-flow merge, cross-link only" decision doesn't cover.

9. **`intelligent-model-selection` is not "registered in binary, absent from ConfigMap".** The downstream registry registers exactly: maas-headers-guard, model-provider-resolver, api-translation, apikey-injection, nemo-request-guard, nemo-response-guard (ipp-ga.md §1, `plugins.go:29–34`). ims exists nowhere in code. B2's relabel ("opt-in, not in default profile") would create a *new* inaccuracy; it should be deleted like base-model-to-header.

10. **EPP parenthetical is backwards.** B2: "3.4/3.5 = Istio InferencePool ext_proc in natural position (post-ipp, before router)". "Post-ipp, before router" is the **3.6-dev reordered** position (`ipp-pre → auth → ipp → EPP → router`). In 3.4/3.5 Istio places the InferencePool filter after the WasmPlugin phases, and the reorder's own code comment says with router-anchored RHCL wasm "the EPP never runs and pool traffic silently falls back to round-robin" (maas-3.5.md §4.1; v0.2.1 envoy-filter = 201 lines, no reorder; HEAD = 368). The design should decide how to honestly depict 3.5 EPP — showing eager pod selection in 3.5 may itself be an inaccuracy.

11. **Loop mode and `flowOrder` are unaddressed.** `execStep` auto-cycles `flowOrder` on loop completion and force-writes `flow-select.value = activeFlow` (`:1483–1491`); loop mode auto-starts 500ms after load (`:1649`). With per-version flow sets, `flowOrder` must be per-version, option repopulation must stay in sync, and cross-version looping must be defined — otherwise the first user interaction after C1 is a select mismatch.

12. **`tips` hit-test has no visibility filter.** Click and hover iterate `Object.keys(tips)` against node rects (`:713–731`); version-hidden nodes remain clickable and cursor-pointer unless the handlers are made version-aware. The inventory recipe notes this; B1's mechanism list does not.

13. **Mobile splash: stats fix is under-specified and the mini-canvas is ignored.** Stats are static HTML (`:121–125`) needing JS and a definition (per-version max? sum? current flow?); the splash's particle animation hard-codes 3.4-era labels (`IPP`, `EPP`, `NIXL`, `Bedrock`…, `:1680+`) which stay stale in every version.

14. **Inspector effort and drift are real and unmitigated.** B3 implies ~10 flow arrays / ~230 steps. At current density (~360 inspector lines for 76 steps, `:955–1269`), that's ~1,100–1,500 lines of hand-keyed payloads, indexed by hard-coded circled numerals (①–㉟), decoupled from the step arrays with no coupling check — any step insertion silently shifts every payload. The design proposes no structural fix (see Suggestions).

## Minor

- Code-site citations are close but slightly off: flow-select is `:148–153` (not :140–154); drawBox glow/stroke block is `:386–400` (≈ as cited); splash badge :118 ✓ exact.
- `drawBounds` IPP section rects sit inside `if (N.ipp)` — always truthy; "version-aware rendering" needs real conditions, and `drawContainer('ipp')` is called unconditionally (`:479–482`).
- Terminology rule (B2) needs an occurrence inventory: legend "IPP Container" (`:189`), `tips.gw` ("IPP (ext_proc)"), `tips.epp` ("An ext_proc filter like IPP"), splash mini-canvas `IPP` label all survive unless C5 catches them.
- Ghost card needs a new render mode: `soon:true` renders "COMING SOON" (`:407–412`), wrong semantics for a runtime-status card; "info icon" doesn't exist in `drawBox`.
- `responses-api/index.html`: besides the engine-duplication debt (now 5+ files sharing the engine incl. `phases/phase1–6.html`), its `agentic` flow is unreachable from its select (dead code) — the provenance banner leaves plan-derived content animating as if implemented.
- `stepOnce` reads `flowMap[activeFlow]` while `execStep` reads the global `flow` (`:1436` vs `:1478`) — both must move to the version-keyed map together.

## Suggestions

- **Cheapest order (revised):** (1) C2-lite first, *without* the version toggle — correct the single scene to 3.5 GA (two-stage split, plugin list, dual callbacks, CRD fix, usage-logs path, EPP honesty). Accuracy ships immediately; no plumbing risk. (2) Port activePathColor properly (activation-color map + errColor exception) — smallest change, independent. (3) Then C1: version toggle + derive the 3.4 scene by subtraction (3.4 is the current scene minus 3.5 additions — nearly free once 3.5 is right). (4) 3.6 praxis scene. (5) Migration last — or cut (below).
- **Scope cuts preserving intent:** drop the *animated* migration flow in favor of the AGC-node overlay + a static state-machine diagram (the design already puts the mechanics in B2/B5 overlays); share auth/RL flows between 3.5 and 3.6 (mechanics identical per facts); keep the ghost card (cheap, high honesty value); consider labeling the untouched current scene "3.4" instead of rebuilding it.
- Make visibility **flow-driven** (tag nodes with `scenes: [...]`, filter in `draw`, `drawBounds`, click, hover), and give EPP a per-version coordinate override rather than moving `N` coords.
- Replace number-keyed `inspStep*` with inspector payloads embedded in (or id-keyed from) the step arrays; generate circled numerals from the index. This eliminates the drift class entirely and cuts the inspector effort roughly in half.
- Decide and document the `praxis-flow.html` relationship (cross-link + provenance banner) **before** building the 3.6 praxis scene, exactly as was done for enmaas-flow.
- Add a coordinate plan (node rects per scene, even as a table in the plan) as a Phase B exit criterion — hand-tuning arrow offsets is where this design's schedule will actually go.
